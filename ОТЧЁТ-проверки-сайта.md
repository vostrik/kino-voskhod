# Отчёт: проверка сайта «Восход» после правок
Дата: 28.09.2026. Проверка: браузерные замеры (localhost) + ручная проверка кода и DOM.

## Что перепроверено и уже в порядке (после первой волны правок)

- CLS = **0.000** (было 0.499), long tasks при загрузке **нет** (был 123 мс).
- Контраст всех проверенных пар текст/фон **≥ 4.5:1**.
- `lang="ru"`, alt-тексты, aria-label у select и кнопок, `:focus-visible`,
  сеансы — настоящие `<button>` с текстовым статусом, картинки WebP в
  `<picture>` с width/height, hero с `fetchpriority="high"`, скрипты `defer`.

Ниже — проблемы, которые **остались** в текущей версии.

---

## Производительность

**П1. Блокирующий styles.css.**
1. Нашёл: `<link rel="stylesheet" href="styles.css">` в `<head>` (index.html:73) — Lighthouse продолжит показывать «Устраните ресурсы, блокирующие отрисовку».
2. Почему плохо: браузер не рисует ничего, пока не скачает и не разберёт весь файл, хотя первый экран уже полностью покрыт инлайн-CSS.
3. Правка: `<link rel="stylesheet" href="styles.css" media="print" onload="this.media='all'">` + `<noscript>`-запас — тот же приём, что уже сделан для шрифтов.

**П2. Расписание вставляется после первой отрисовки.**
1. Нашёл: `#schedule` пуст в HTML и заполняется только в `DOMContentLoaded` (app.js); на медленной сети контент появляется с опозданием и сдвигает блок «О кинотеатре» и футер вниз (на быстром localhost замер CLS = 0, риск проявляется на 3G).
2. Почему плохо: пользователь успевает увидеть страницу без расписания, затем контент прыгает — можно промахнуться по ссылке или сеансу.
3. Правка: задать `#schedule { min-height: ~600px }` (или скелетон-заглушку) в CSS, чтобы место было зарезервировано до прихода JS.

**П3. Скачок текста при подмене шрифта (FOUT).**
1. Нашёл: шрифты подключены с `display=swap` — до прихода Roboto/Playfair текст рисуется Arial с другими метриками, затем переливается (замер локально 0 из-за кеша; на реальной сети сдвиг будет).
2. Почему плохо: строки меняют ширину и высоту после загрузки шрифта — «дёрганый» первый экран, вклад в CLS.
3. Правка: самохостинг шрифтов с `size-adjust`/`ascent-override` под метрики Arial (или `font-display: optional` для первого экрана) — подмена станет незаметной.

**П4. Лишнее начертание в запросе Google Fonts.**
1. Нашёл: URL запрашивает `Roboto:wght@400;500;700`, но `font-weight: 500` нигде в CSS не используется (только 400 и 700).
2. Почему плохо: браузер держит лишнее правило @font-face и может скачать ненужный файл (~15–20 КиБ на реальной сети).
3. Правка: убрать `;500` из обоих URL шрифтов в `<head>` (index.html:79, 81).

**П5. Полный перерендер расписания на каждое событие resize.**
1. Нашёл: `window.addEventListener("resize", renderSchedule)` (app.js:145) — на каждый «тик» изменения окна: `JSON.parse(JSON.stringify(SESSIONS))`, пересчёт популярности по всем 280 сеансам и перестройка innerHTML.
2. Почему плохо: при перетаскивании окна — десятки перерендеров в секунду, главный поток занят, а сфокусированная кнопка сеанса уничтожается и фокус падает в начало документа.
3. Правка: убрать обработчик вовсе (рендер не зависит от размеров окна) либо обернуть в debounce ~150 мс; клон SESSIONS и популярность кешировать.

**П6. Принудительный reflow на каждое событие scroll.**
1. Нашёл: обработчик прогресс-бара (app.js:139–143) на каждый scroll читает `document.documentElement.scrollHeight` и пишет `style.width` — чередование чтения и записи геометрии.
2. Почему плохо: браузер вынужден синхронно пересчитывать раскладку на каждый кадр скролла — на слабых телефонах скролл подёргивается.
3. Правка: считать высоту один раз (обновляя по resize), менять `transform: scaleX()` вместо `width` и оборачивать запись в `requestAnimationFrame`.

**П7. poster-7.webp — выброс по весу.**
1. Нашёл: img/poster-7.webp весит 66,5 КиБ — втрое тяжелее медианы постеров (9–23 КиБ); шумная фактура фото плохо сжимается.
2. Почему плохо: одна картинка съедает четверть всего веса постеров и задерживает догрузку нижних карточек.
3. Правка: пересжать именно этот постер с качеством ~60 или лёгким шумоподавлением — у учебного макета допустимо.

**П8. Cache-Control: max-age=600 (инфраструктура).**
1. Нашёл: GitHub Pages отдаёт все статические файлы с кешем на 10 минут (замер из первого отчёта, кодом сайта не меняется).
2. Почему плохо: при повторном визите браузер заново проверяет и качает ~580 КиБ — повторные заходы медленные.
3. Правка: на GitHub Pages заголовки не настраиваются — нужен service worker с Cache API либо хостинг с настраиваемыми заголовками (Netlify `_headers`: `max-age=31536000, immutable`).

## Доступность

**Д1. Нарушена иерархия заголовков, нет `<h1>`.**
1. Нашёл: первый заголовок на странице — `h3.hero__title`, карточки — h3, блок «О кинотеатре» — h3 без h2-обёртки; h1 и h2 отсутствуют (проверка DOM).
2. Почему плохо: скринридер строит навигацию по заголовкам — без h1/h2 структура «страница → раздел → фильм» нечитаема, быстрый переход по разделам невозможен.
3. Правка: логотип «Восход» сделать `h1` (в шапке), добавить скрытый `h2` «Расписание сеансов» перед `#schedule` и `h2` «О кинотеатре» вместо h3, карточки оставить h3.

**Д2. Модальное окно недоступно как диалог.**
1. Нашёл: `#modal` — обычный `div` без `role="dialog"`/`aria-modal`; в коде нет keydown-обработчика (Esc не закрывает), `openModal()` не переносит фокус в окно, Tab из окна уходит в шапку под затемнением, после закрытия фокус теряется (grep по app.js).
2. Почему плохо: незрячий пользователь не узнает, что открылось окно, не выберется из него Esc, клавиатурный фокус «проваливается» в невидимый фон.
3. Правка: `role="dialog" aria-modal="true" aria-labelledby` на `#modal`, при открытии — `.focus()` на кнопку закрытия, ловушка Tab внутри окна, Esc → `closeModal()`, после закрытия — возврат фокуса на выбранный сеанс.

**Д3. Нет ссылки «Перейти к содержимому».**
1. Нашёл: первый элемент `body` — индикатор прокрутки; skip-link отсутствует (проверка DOM), перед расписанием — шапка с 5 ссылками и 2 кнопками.
2. Почему плохо: на каждой навигации с клавиатуры пользователь обязан протабать всю шапку, чтобы попасть к расписанию.
3. Правка: первым элементом `body` добавить `<a class="skip-link" href="#schedule">Перейти к расписанию</a>` — визуально скрыта, показывается при фокусе.

**Д4. Одиннадцать «мёртвых» ссылок `href="#"`.**
1. Нашёл: 5 ссылок меню и 6 ссылок футера ведут на `#` (проверка DOM): «Расписание» не прокручивает к расписанию, «Контакты» — к контактам.
2. Почему плохо: ссылка скроллит страницу наверх и ничего не открывает; скринридер объявляет рабочую навигацию, которая никуда не ведёт.
3. Правка: проставить реальные якоря (`href="#schedule"`, `href="#about"`, `id="contacts"` футеру) или временно сделать нерабочие пункты `<button>` с `disabled`-стилем.

**Д5. `alert()` как канал сообщений.**
1. Нашёл: 3 места — кнопка поиска (index.html:101), «Оплатить» (index.html:188), «мест нет» (app.js:130).
2. Почему плохо: модальный системный диалог перебивает скринридер, блокирует страницу, а после закрытия фокус падает в непредсказуемое место.
3. Правка: выводить сообщения инлайн — например, регион `<div aria-live="polite">` над расписанием для ошибок и текст в теле модального окна для демо-оплаты.

**Д6. Мелкие цели касания у чипов сеанса.**
1. Нашёл: высота кнопки сеанса — **39px** (замер DOM), рекомендация WCAG 2.5.8 / Material — минимум 44px.
2. Почему плохо: на телефоне легко попасть пальцем в соседний сеанс и купить билет не на тот сеанс.
3. Правка: увеличить вертикальный padding `.session` с 9px до 12–13px (высота станет 44–46px), для мобильных — `min-height: 44px`.

**Д7. Плавный скролл игнорирует prefers-reduced-motion.**
1. Нашёл: кнопка «Купить билет» вызывает `scrollIntoView({behavior:'smooth'})` (index.html:102) без проверки настройки ОС.
2. Почему плохо: у пользователей с вестибулярными нарушениями плавная прокрутка вызывает головокружение и тошноту.
3. Правка: `var smooth = !matchMedia('(prefers-reduced-motion: reduce)').matches;` и передавать `behavior: smooth ? 'smooth' : 'auto'`.
